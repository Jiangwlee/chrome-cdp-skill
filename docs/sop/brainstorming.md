# SOP: 需求头脑风暴

本文档描述 Coding Agent 在收到功能需求后、开始提问前的头脑风暴流程。
目标是通过主动调查把问题想清楚，而不是把调查义务转移给用户。

## 核心原则

**先调查，后提问。** 问题应聚焦于业务需求，而非实现细节。
实现细节可以通过调查自行解决；业务意图只有用户才能确认。

## 流程

### 第一步：复述意图

用一句话概括用户的目标，确认方向正确。

### 第二步：主动调查

在提问之前，先做能做的调查。调查来源包括：

**读现有代码**
- 读同类 SOP 的脚本和参考文档，了解已有模式。
- 读开发指南（如 `sop-development.md`），了解规范要求。
- 读索引文件（如 `SKILL.md`、`index.md`），了解现有边界。

**看真实页面**（适用于 Chrome CDP 场景）
- 用 `cdp.mjs list` 确认目标 tab 是否已打开。
- 用 `snap` 了解页面无障碍结构和主要区域。
- 用针对性的 `eval` 小探针确认 DOM 结构、URL 规律、数据格式。
- 必要时交互（点击、输入、翻页），观察页面行为。

调查目标：在提问之前，尽量自行回答以下问题：
- 页面/数据的实际结构是什么？
- 现有实现模式是什么？
- 哪些细节可以从代码或页面直接获得？

### 第三步：集中提问

调查完成后，只问调查无法回答的问题，并且只问**业务层面**的问题：

- 场景边界：哪些情况在范围内，哪些不在？
- 输出目标：结果给谁用、在哪里用？
- 优先级：MVP 先做哪一步？
- 使用姿势：典型的操作流程是什么？

**不问**：如何实现某个技术细节（那是调查的责任）。

一次性把所有问题列出来，不要多轮追问。

### 第四步：写设计摘要

用户回答后，写 ≤150 字的设计摘要（目标、范围、关键决策），请用户确认后再开始实现。

## 反模式

| 错误做法 | 正确做法 |
|---|---|
| 直接列出实现问题（"搜索 URL 是什么？"） | 打开页面，`eval` 一下就知道了 |
| 问 DOM 结构、选择器、API 路径 | snap + eval 调查，不问用户 |
| 在调查前就提问 | 调查完、问题收敛后再提问 |
| 多轮分散提问 | 一次性列出所有问题 |

## 豁免条件

以下情况直接实现，跳过头脑风暴：
- 需求已包含明确的输入、输出和验收标准。
- 用户明确说"直接做"或"不用澄清"。
- 变更范围极小（单文件 bugfix、文字修改、格式调整）。
